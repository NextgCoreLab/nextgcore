NextGCore Documentation

PCF Configuration

The PCF (Policy Control Function, nextgcore-pcfd) makes access-, session-, and application-level policy decisions for the 5G core, per TS 29.507, TS 29.512, TS 29.514 and TS 29.525 (as cited in the daemon’s source comments). Its SBI router (pcf_sbi_request_handler in src/bins/nextgcore-pcfd/src/app.rs) serves five services: Npcf_AMPolicyControl (/npcf-am-policy-control/v1/policies), Npcf_SMPolicyControl (/npcf-smpolicycontrol/v1/sm-policies), Npcf_PolicyAuthorization (/npcf-policyauthorization/v1/app-sessions), Npcf_UEPolicyControl (/npcf-ue-policy-control/v1/policies), and Npcf_EventExposure (/npcf-eventexposure/v1/subscriptions, TS 29.523), plus a N1MessageNotify callback route (/npcf-ue-policy-control/v1/notify/{polAssoId}/n1-message-notify, TS 29.518 per code comments) on which the AMF returns the UE’s MANAGE UE POLICY COMPLETE/REJECT. The binary itself is a thin wrapper: main.rs only calls nextgcore_pcfd::run(); all logic lives in the library crate (lib.rs/app.rs, Wave-6 lib-targetization).

Configuration is split between a YAML file (default path /etc/nextgcore/pcf.yaml, overridable with -c/--config), command-line flags, and an unusually large set of environment variables. The YAML file supplies the SBI address/port (after the CLI flags, #1312) and advertised host, an optional FQDN, and the NRF URI; capacities and TLS-related flags are CLI-only; UE-policy delivery, URSP rules, UAV gating, the local PLMN, OAuth2 enforcement, and the OTLP endpoint are env-var driven.

Honesty note: PCF behavior is validated by this project’s own unit tests and matched-simulator Docker E2E runs, not by third-party conformance certification. Several pieces are explicitly bespoke or partial: the urspRules member the PCF reads from the UDR UePolicySet is a provisioning-side convention of this deployment, never a 3GPP wire field (documented as such in ue_policy.rs); the UAV flight-zone gate uses a hardcoded geofence (lat 37–38, lon −123…−122); the intent_policy module is Rel-20 research scaffolding not wired to any live handler; the --tls* flags do not enable TLS on the live HTTP/2 listener (see below); and -k/--kill is refused with an error and -l/--log-file is accepted but unused (no file logging is wired in init_logging).

pcf.policy.udr_requiredboolfalseWhat a policy create does when an NRF is configured, the NRF does not answer the UDR discovery (an error or the 2 s discovery bound), and no UDR is known (#1639, operator decision): none discovered since start-up or the remembered one expired (a remembered UDR past its validityPeriod counts as none known, operator-confirmed on #1639), and no still-valid NRF answer saying none is deployed (it expires after the SearchResult’s validityPeriod, at most 24 h). true: the AM policy create, the SM policy create and UE policy delivery treat it as an outage, so the creates are refused 500 SYSTEM_FAILURE (TS 29.500 Table 5.2.7.2-1) and leave nothing behind. Fail closed: a PCF started before its NRF refuses creates until the NRF answers. false: the local default policy, as before #1639. Fail open: until the first discovery, creates get the built-in policy without the subscriber’s restrictions. The specs are silent on this case (TS 29.512 §4.2.2.2, TS 29.507, TS 29.510). It does not apply when no NRF is configured, when the NRF lists no UDR, or to an Emergency DN, which never reads the UDR. Shipped: true in the Helm chart (pcf.policy.udrRequired in values.yaml, where anything but a boolean fails the render) and in k8s/manifests/configmap.yaml, the base of the EKS profiles (and of the demo-d441a overlay’s pcf.yaml); false in docker/rust/configs/5gc/pcf.yaml, which every compose file mounts. Anything but a YAML boolean ("true", yes, 1) fails startup. The value in force is logged at startup.

Parsed-but-inert / decorative YAML fields

The daemon deserializes only the fields above; unknown YAML keys are silently ignored by serde. In the shipped example file:

  • db_uri opens the subscriber store (#1457). The top-level db_uri (or --db-uri, which wins) names the MongoDB that SM policy creates and re-evaluations read each subscriber’s 5QI, ARP, Session-AMBR and PCC rules from, and that AM policy reads ueAmbr from when the UDR supplies none. It is opened at startup, before the boot restoration and before the SBI server; an unreachable server is retried 5 times, 2 s apart, and then fails startup (about 13 s), as does a malformed URI. A SIGTERM during that wait exits cleanly. When the URI sets no serverSelectionTimeoutMS / connectTimeoutMS, pcfd sets each to 1000 ms (the driver default is 30 s), so a startup attempt and a runtime read against a store that has gone away both fail within about 1 s; the read then takes the fallback below, inside the SMF’s 3 s Npcf budget. A value the URI sets is kept. Store reads run with block_in_place, so a slow read does not hold a runtime worker away from other requests, the NRF heartbeat or /metrics. Before #1457 the key was never read, so every session got the built-in default. With no db_uri configured the PCF still starts, logs a warning, and authorises the built-in defaults (see Behavior notes).
  • logger.level is read; logger.file.path is inert. The log level is -e/--log-level when given, else this file’s logger.level, else info; RUST_LOG, when set, overrides all three (#691). No file output is wired (the -l/--log-file flag is accepted but unused).
  • global.max.ue / global.max.peer are inert. Context capacities come from the CLI flags --max-ue (1024) and --max-sess (4096).
  • No pcf.metrics.server[] (removed from the shipped config, #1312): the daemon starts no metrics HTTP server; its only telemetry export is OpenTelemetry OTLP via OTEL_EXPORTER_OTLP_ENDPOINT.
  • pcf.tls.* is inert. No code reads this section. The CLI --tls/--tls-cert/--tls-key flags serve the live listener over TLS under the dev SBI profile (#1795). Under production (the default) it serves mutually-authenticated TLS and requires an access token whatever they say, and the advertised scheme says https either way.

Behavior notes

  • Durable state (optional, off by default). With --state-file or NEXTGCORE_PCF_STATE_FILE set, the four primary context lists — AM policy associations, SM policy UE contexts, PDU sessions and AF application sessions — are written to a JSON snapshot on every mutation and reloaded at boot, before the SBI server accepts anything. Without it, a restart leaves the AMF and SMF holding association URIs that 404, and the SMF cannot even tear a session’s policy down cleanly. Four things worth knowing operationally:

    • The seven secondary lookup indexes are rebuilt, not persisted (supi→AM, associationId→AM, supi→SM, smPolicyId→session, IPv4→session, IPv6-prefix→session, appSessionId→app). A persisted index could disagree with its list and resolve to the wrong record; deriving it makes that impossible. Every lookup that worked before a restart works after it.
    • The four internal id allocators resume above the restored maximum. Left at 1 they would hand out ids that restored records already hold, and the insert would silently replace a live association with a different subscriber’s.
    • An unreadable snapshot, or one written by a newer pcfd, fails startup and is left untouched rather than being overwritten from empty state. Move the file aside to start fresh.
    • Persisting is synchronous on every mutation, so an association the PCF has acknowledged is durable. Unlike nwdafd there is no periodic sweep, so this is one write per consumer request rather than per tick.
    • Restoration signalling (#193). The four record lists are read per record, so one entry whose schema moved does not discard the snapshot — but a skipped sessions record is an SM policy association the SMF still holds, and every later update or delete on it would get a bare 404. At boot, before the SBI server accepts anything, the PCF now POSTs {notificationUri}/terminate with a TerminationNotification (TS 29.512 §4.2.4) for each such association, so it is closed rather than left to rot. The notificationUri and smPolicyId are salvaged from the raw record — the record failed typed deserialisation, not JSON parsing, so both are still readable, and without that salvage there would be nobody to tell. Limits: the cause is UNSPECIFIED, because no enumerated TS 29.512 cause describes “the producer lost its own record”; delivery is fire-and-forget like every other PCF notification; a record that yields neither member is counted as unreachable and logged at error rather than silently dropped; and nothing is emitted when no state file is configured, since then nothing was restored. This is the PCF half of #193 — the SMF’s session-level half is in SMF Configuration.

  • Policy associations and app sessions are managed only by their creator (#1937). AM and UE policy associations (the AMF), SM policy associations (the SMF) and AF app sessions with their events subscription (the AF/NEF) record the verified identity of the NF that created them (nextgcore_sbi::owner_binding: client certificate unless it names a relay, else token sub; the two must agree). This identity is persisted with the AM/SM/app records. GET, update and delete (including POST .../delete and .../events-subscription) by any other caller are refused 403 before anything is read or changed. Under the production SBI profile an anonymous create is refused, and a record restored from before #1937 is frozen. UE policy associations are in memory only.

  • A frozen restored record lapses (#1992). Under the production profile, an AM/SM/app record restored without an owner lapses 24 h after the first restart that finds it; the lapse is written back, so later restarts do not extend it. Its NF then gets 404 rather than 403 for ever.

  • AMF relocation (#1992, R30 on #2013). A new AMF that updates an AM or UE policy association with the Notification URI and the GUAMI (TS 29.507 §4.2.3.2, TS 29.525 §4.2.3.2) takes it over only if the NRF (NF discovery by the caller’s verified nfInstanceId) returns an AMF profile whose amfInfo.guamiList includes that GUAMI. The caller’s identity is its certificate’s NF instance ID when it calls directly, and then the certificate must also name AMF among its NFTypes; behind an SCP or SEPP it is the verified token subject, and the NRF profile is what types it. A token with no certificate is refused. A relocation relayed by a SEPP is refused outright, and so is one for a GUAMI the NRF lists for AMFs of more than one AMF Set (#2035). Every page of the AMF discovery is read, and a result that does not end within 50 pages is refused. No NRF, an NRF error, no matching profile or no GUAMI refuses it (403, nothing changed). The previous AMF is then refused.

  • NRF registration and heartbeat: at startup the PCF PUTs one NFProfile (/nnrf-nfm/v1/nf-instances/{id}) advertising all five services it serves — npcf-am-policy-control, npcf-smpolicycontrol, npcf-ue-policy-control, npcf-policyauthorization and npcf-eventexposure — each with its own ipEndPoints and allowedNfTypes, plus heartBeatTimer: 10 and an NF-level allowedNfTypes: [AMF, SMF, AF, NEF, NWDAF] (the union over the services). Before #90 there were two registrations per startup, under two different nfInstanceIds and with two different service sets, only one of which was heartbeaten; there is now a single profile builder (PCF_SERVICES in sbi_path.rs) so the advertised set cannot drift from what the router serves. It then spawns a heartbeat worker every 5 s that PATCHes a real /load gauge (TS 29.510 §5.2.2.3.2 per code comment): load = (AM + SM policy associations) × 100 / (2 × max_ue), clamped 0–100. Registration failure is non-fatal — the PCF logs a warning and “will operate without NRF”. The same NF instance ID doubles as pcfId in BSF PcfBinding registrations (TS 29.510 per comment).

  • Policy-control event exposure (TS 29.523): POST /npcf-eventexposure/v1/subscriptions creates an Individual Policy Control Events Subscription (201 + Location), and GET/PUT/DELETE …/subscriptions/{subscriptionId} read, replace and remove it. notifUri, notifId and a non-empty eventSubs are mandatory; a notifUri that is not an absolute http(s) URI is rejected at ingress rather than failing silently at every notification. When an event fires, every subscription that asked for it and whose filterDnns admits the event’s DNN is POSTed a PcEventExposureNotif at its notifUri, retried on transport/5xx failure and charged against eventsRepInfo.maxReportNbr; subscriptions and their report counts are persisted, so maxReportNbr survives a restart. Only four PcEvent tokens have a producer in this build — AC_TY_CH (SM policy update whose accessType differs from the stored session’s), PLMN_CH (AM policy update whose GUAMI PLMN genuinely moved), and SUCCESS_UE_POL_DEL_SP / UNSUCCESS_UE_POL_DEL_SP (the UE-policy MANAGE UE POLICY COMPLETE/REJECT outcome). The other nine enum tokens are not faked: a subscription is accepted when at least one requested event is reportable and refused with 400 EVENT_NOT_SUPPORTED when none is, since a subscription that can never fire would leave the consumer waiting forever. An unrecognised token is NOT rejected — PcEvent is anyOf [enum, string], so an unknown token is forward-compatibility with a later release.

  • Mandatory-IE rejection: AM and UE policy create require notificationUri, supi and suppFeat (TS 29.507 §5.6.2.3 / TS 29.525 per comments); SM policy create requires supi, pduSessionId, dnn, pduSessionType, notificationUri and sliceInfo.sst (TS 29.512 §5.6.2.3). Anything missing → HTTP 400 with cause MANDATORY_IE_MISSING. suppFeat is negotiated (consumer ∩ producer): producer masks are 0x0 for AM/UE-policy/PolicyAuthorization and 0x103 for SM (TSC, ResShare, and PCSCF-Restoration-Enhancement, feature 9). The SM mask negotiated at create is kept on the session: a POST /npcf-policyauthorization/v1/app-sessions/pcscf-restoration for a session that negotiated feature 9 sends the SMF an UpdateNotify whose decision is {"pcscfRestIndication": true} (TS 29.512 §4.2.3.18). For a session that did not negotiate it, the session’s policy is re-sent, with a WARN (#1398). Updates use the spec custom operations POST …/policies/{id}/update and POST …/sm-policies/{id}/{update,delete}; legacy PATCH/DELETE arms are kept for backward compatibility. Unmatched routes get 405.

  • P-CSCF restoration is answered per caller (#1991, #2016). Only the SMF that owns the SM policy, or an AF/NEF that owns an app session on the PDU session, may restore it. The PCF identifies the session among the caller’s own sessions only. So a session the caller may not restore is answered exactly as no session is, with 500 PDU_SESSION_NOT_AVAILABLE (TS 29.514 §4.2.2.27) and the same detail. A caller cannot probe which UE addresses have sessions. Several of the caller’s sessions matching is still a 500 ambiguity. A certificate and token naming different NFs get 403 before any lookup.

  • Policy-data sources: the subscriber store named by db_uri (see above). When a read fails at runtime — no store configured, an unknown subscriber, DNN or slice — nudr_handler falls back to built-in defaults for SM: 5QI 9, ARP 8, session AMBR 100/100 Mbps, no PCC rules. AM has no default: with no subscribedUeAmbr from the UDR and no UE-AMBR in the store (failed read, unknown subscriber, a document without ambr, or an ambr with only one direction, since TS 29.571 makes both mandatory), the AM policy carries no ueAmbr and the AMF keeps its own (#1460; before it, 1 Gbps up/down was invented). A re-evaluation of a live session keeps the decision it was built from instead (#1383). On the live SM path the PCF additionally does a bounded (3 s) NRF-discovered nudr-dr GET of SmPolicyData (TS 29.519 per comment) and maps only the online/offline charging flags into the decision.

  • UDR outage on the create path (#1597, #1613, #1621, #1639): the AM policy create, the SM policy create and UE policy delivery each read the UDR with a bounded (3 s) nudr-dr GET (am-data, sm-data, ue-policy-set).

    • Nothing provisioned: only a 404 means this, and keeps the local defaults above. So does a PCF that knows of no UDR deployed: no NRF configured, or an NRF that lists none (or whose last answer did, or that reports the remembered UDR deregistered).
    • No UDR known and the NRF does not answer (#1639): nothing remembered (no UDR discovered since start-up, or what was learned expired) and no still-valid NRF answer saying none is deployed (such an answer expires after its SearchResult validityPeriod, at most 24 h, as a remembered UDR does). pcf.policy.udr_required decides: true, the create is refused 500 SYSTEM_FAILURE as for an outage; false, the local default applies. Emergency DNs are never refused by it.
    • Finding the UDR: the PCF remembers the last UDR the NRF listed, with its NF instance id, for the SearchResult’s validityPeriod (TS 29.510 Table 6.2.6.2.2-1), capped at 24 h. The policy-data subscription task fills this too.
      • The NRF fails or times out: the remembered UDR is read.
      • The NRF answers but lists no UDR: the remembered instance’s NFProfile is retrieved (TS 29.510 §5.2.2.9). A 404 with a ProblemDetails means it deregistered: it is forgotten and the local default applies. A 404 without one, or with cause RESOURCE_URI_STRUCTURE_NOT_FOUND, says the path was not understood (TS 29.500 Table 5.2.7.2-1 and its NOTE 5), not that the UDR is gone, so it reads the remembered UDR like any other unusable answer (#1653). Like every pcfd NRF call, the retrieval carries no access token, so an NRF that sets nrf.sbi.oauth2.require_server refuses it, and the discovery before it (#1667). nfStatus SUSPENDED (missed heartbeats) or UNDISCOVERABLE is an outage, so the create is refused 500 without reading the UDR. Any other answer reads the remembered UDR.
      • Timing: discovery and the profile check together get at most 2 s of the bound, so the GET keeps at least 1 s.
    • Outage: every other GET outcome. That is a 5xx, any other 4xx (a 403 from a token-scope misconfiguration included), a 3xx, a 200 whose body is empty or not JSON, a refused connection, or no answer within the bound. The AM and SM creates are then refused 500 SYSTEM_FAILURE (TS 29.500 Table 5.2.7.2-1) and leave no association or session behind. An AM policy update keeps the policy the association holds, and UE policy delivery sends nothing.
    • Emergency DNs: an SM policy create whose dnn is in pcf.policy.emergency_dnns, compared on its Network Identifier so sos.mnc001.mcc001.gprs matches sos (TS 23.003 §9.1), does no UDR read at all (TS 29.512 §4.2.2.2: no subscription check with the UDR for an Emergency DN), so a UDR outage never refuses an emergency session.

  • URSP delivery (UE policy): on UE-policy create the PCF builds a MANAGE UE POLICY COMMAND (TS 24.501 Annex D / TS 24.526 per comments) and delivers it via the AMF’s N1N2MessageTransfer, subscribing for the uplink result before the transfer (TS 29.525 §4.2.2.2 order). Rules come from the UDR UePolicySet urspRules extension when provisioned, else a static catch-all default (dnn: internet, sst 1). The association stays Pending until a COMPLETE arrives; T3501 (default 30 s) retransmits exactly once, then marks the delivery Failed — fail-closed, never a fake Delivered.

  • UAV gating and BSF bindings: an SM policy create whose DNN matches PCF_UAV_DNN (default uav) passes an altitude/flight-zone gate (Rel-18, TS 23.256) and is rejected with HTTP 403 UAV_FLIGHT_NOT_AUTHORIZED when out of policy. The gate fails CLOSED (#90): this PCF has no UAS-NF client, so it cannot perform the USS/UTM authorisation exchange TS 23.256 requires, and it therefore refuses a UAV session unless the operator has provisioned BOTH PCF_UAV_AUTHORIZATION and PCF_UAV_ZONE, AND a PCF_UAV_POSITION to gate. Previously it self-granted CAA-PCF-DEFAULT unconditionally against a hardcoded California geofence with an in-zone default position, so every UAV session was authorised — including ones that should have been refused. A rejected session is now also removed from the context; before #90 each refusal leaked one PcfSess. Each SM policy create/delete also registers/deregisters a PcfBinding at the BSF (TS 29.521). A binding whose 201 lands after its SM policy was deleted or replaced is deregistered at once, not left at the BSF (#1877). A deregistration that fails (no BSF discoverable, no answer, a non-2xx other than 404) is parked and retried every 30 s until the BSF answers 2xx or 404. A pass ends at the first failure (they all go to the one BSF), and the one that failed goes to the back of the queue, so no binding keeps the others from their turn. An unreachable BSF costs one request timeout per 30 s pass. At most 4096 are kept; the oldest is evicted and counted abandoned. A 4xx refusal other than 404 is not retried (refused), and one parked for 24 h is given up (expired). Metrics pcf_bsf_deregistrations_pending and pcf_bsf_deregistrations_reconciled_total{result} (delivered, refused, expired, abandoned). Memory-only.

  • UDR policy-data subscription (#299, #1458): once the SBI server listens, a background task discovers a UDR and POSTs a PolicyDataSubscription (TS 29.519 §5.2.10) for /nudr-dr/v2/policy-data/ues, so a subscriber edit re-authorises live SM policy associations. It does not block startup. Until the subscribe succeeds it retries with a backoff doubling from 1 s to 30 s, so a UDR that registers after the PCF (the EKS race behind #1458) is picked up. When the UDR confirms an expiry, the subscription is renewed with a PUT on its resource (§5.2.11) half its lifetime early, at most 60 s early; a 404 creates a new one. Every PCF_POLICY_DATA_AUDIT_SECS the task re-discovers the UDRs and GETs the subscription. The subscription is kept while its UDR is listed anywhere in the result (NRF order is not stable); when the NRF lists other UDRs but not this one, the old subscription is DELETEd there and a new one made; a 404 on the GET subscribes again; an unreachable NRF or UDR leaves it in place. Each request, discovery included, is bounded at 3 s. A renewal answered 204 keeps the lifetime confirmed before. At shutdown the task stops and the subscription is DELETEd at the UDR it was made at.
