NextGCore Documentation

AMF Configuration

nextgcore-amfd (Access and Mobility Management Function) reads a single YAML file, /etc/nextgcore/amf.yaml by default (override with -c/--config). Configuration is intentionally forgiving: every field is Optional in the typed config structs, and a missing/unreadable/unparsable file or missing amf: section logs a warning and continues with built-in defaults rather than failing startup.

Honesty note: this configuration surface has been validated against matched nextgsim peers and in-process strict-peer tests; it is not third-party certified for 3GPP conformance.

Example (configs/amf.yaml)

# NextGCore AMF Configuration
# PLMN 999-70, TAC 1, S-NSSAI SST=1

amf:
  amf_name: "NextGCore AMF"

  guami:
    - plmn_id:
        mcc: "999"
        mnc: "70"
      amf_id:
        region: 1
        set: 1
        pointer: 1

  tai:
    - plmn_id:
        mcc: "999"
        mnc: "70"
      tac: 1

  plmn_support:
    - plmn_id:
        mcc: "999"
        mnc: "70"
      s_nssai:
        - sst: 1

  security:
    integrity_order: ["NIA2", "NIA1", "NIA0"]
    ciphering_order: ["NEA2", "NEA1", "NEA0"]

  # Which gNBs a CM-IDLE UE is paged on; see "Paging strategy" below.
  # paging:
  #   strategy: registration-area

  # REGULATORY switch, default true. Read "Unauthenticated emergency service"
  # below before changing it: this key decides whether an emergency call
  # connects when the AUSF is unreachable, and the correct value is a matter of
  # local law, not of taste.
  emergency:
    allow_unauthenticated: true

Behavior notes and caveats

  • Lenient loading: a missing config file, YAML parse error, or missing amf: section logs a warning and starts the AMF with defaults — it does not abort. Typos in key names are therefore silently ignored; check the startup log lines (Configured GUAMI: ..., AMF configuration loaded: N GUAMI, N TAI, N PLMN support) to confirm what was actually applied. Three exceptions abort start-up, and a refused file applies nothing:
    • a plmn_support entry left with no usable S-NSSAI (none listed, or every one SST 0, which is refused as no slice — TS 23.501 §5.15.2.2). The NG Setup Response’s Slice Support List must hold at least one (TS 38.413 §9.3.1.17).
    • a plmn_support or guami list that resolves to nothing (empty, or no entry with a usable PLMN ID). The NG Setup Response’s PLMN Support List and Served GUAMI List must each hold at least one (TS 38.413 §9.2.6.2). Each list the file names (guami, tai, plmn_support, security.integrity_order, security.ciphering_order) replaces the AMF’s list; a list the file leaves out keeps its default.
    • a malformed mcc or mnc in any guami, tai or plmn_support entry: a YAML number, or a string that is not 3 (MCC) or 2-3 (MNC) digits (#2115). The error names the entry, e.g. amf.guami[0].plmn_id.mcc=1 reached the configuration as a number, not a string.
  • PLMN digits are strings (#2115): write mcc and mnc quoted (mcc: "001", mnc: "070"). A YAML number is refused at load, even one that lost nothing (mcc: 999): once a value is a number its leading zeros are gone (a YAML 1.1 re-dump turns "001" into 1), the AMF cannot know which PLMN was meant, and MNC 70 and 070 are different PLMNs (TS 23.003 §2.2). The AMF used to accept the number and read its digits from the left, so mcc: 1 configured MCC 100. A 2-digit MNC is encoded with the filler digit per standard PLMN encoding. The Helm chart refuses a numeric global.plmn on the deploy side with the same rule and renders it quoted (#2069).
  • Empty security lists: if security is omitted, the integrity/ciphering preference lists in the AMF context stay empty; supply explicit orders (as in the example) for deterministic algorithm selection.
  • Multiple NRF entries in sbi.client.nrf are parsed but only the first is used — additional entries are currently inert.
  • amf.ngap.server[0] and amf.sbi.server[0] are the NGAP and SBI listen addresses (#1311). --ngap-addr and AMF_SBI_ADDR/AMF_SBI_PORT override them; with neither, loopback (#1308). There is no amf.metrics.server (#1312); the metrics endpoint is NEXTGCORE_METRICS_BIND:AMF_METRICS_PORT.

Network Slice Admission Control (#1876)

With an NSACF configured or discoverable, a registering UE is counted in on each Allowed S-NSSAI with Nnsacf_NSAC_NumOfUEsUpdate INCREASE, and counted out again with DECREASE (TS 23.502 §4.2.11.2). Before #1876 the AMF only ever sent the INCREASE.

  • Count-in. One INCREASE per Allowed S-NSSAI. A denied S-NSSAI (maximum number of UEs reached) is rejected and the registration goes on with the others (#1942, TS 23.502 §4.2.11.2): it leaves the Allowed NSSAI and goes in the Registration Accept’s Rejected NSSAI with cause “S-NSSAI not available in the current registration area”. That is the cause TS 24.501 §5.5.1.2.4 gives a UE without Extended rejected NSSAI support, and this AMF does not offer Extended rejected NSSAI. Only when every S-NSSAI is rejected is the registration rejected, with 5GMM #62 “No network slices available” and the S-NSSAIs in the reject’s Rejected NSSAI (§5.5.1.2.5). An NSACF that is absent, unreachable or answers unexpectedly degrades open: the UE is admitted, but nothing was counted, so nothing is recorded. An INCREASE that got no answer at all may have been applied, so a precautionary DECREASE follows. That DECREASE is not retried.
  • Count-out. A DECREASE on every S-NSSAI the NSACF admitted the UE to, sent to the NSACF that granted it under the same nfId. This happens on every deregistration (UE-initiated, network-initiated, local, implicit), for an S-NSSAI dropped from the Allowed NSSAI by a later registration, and for every admission of a UE whose registration is rejected because no S-NSSAI was admitted.
  • Reconciler. A DECREASE that fails (no answer, a 5xx, a refused token) is parked and retried every 30 s until the NSACF accepts it; a 404 counts as accepted. At most 4096 are kept, and the oldest is evicted and counted abandoned. A parked DECREASE for an (SUPI, access type, S-NSSAI) that has been admitted again since is superseded and not sent: the NSACF counts a UE once, so it would count the live registration out. The set is memory-only, like amfd’s UE contexts. #1945: a DECREASE is bounded by its own 2 s connect and 5 s request timeouts, and an INCREASE waits up to 10 s for one in flight for the same UE and S-NSSAI, so ordinarily the DECREASE lands first. If the NSACF applies it later anyway, for example after the INCREASE stopped waiting, the AMF sends the INCREASE again once the DECREASE ends (amf_nsac_ue_recounts_total); an INCREASE of a UE the NSACF already counts is idempotent. Every DECREASE (immediate, precautionary or reconciled) is registered as in flight in the same step as its check, so a quick re-registration’s INCREASE for the same UE and S-NSSAI waits for it to land first. A DECREASE that finds an INCREASE being decided is not sent: that INCREASE takes the count over and sends the DECREASE afterwards if it does not count the UE (#1940 review). Every DECREASE (immediate, precautionary or reconciled) is registered as in flight in the same step as its check, so a quick re-registration’s INCREASE for the same UE and S-NSSAI waits for it to land first. A DECREASE that finds an INCREASE being decided is not sent: that INCREASE takes the count over and sends the DECREASE afterwards if it does not count the UE (#1940 review).

NSACF unreachable: degrade open (operator policy, #1999)

TS 23.502 §4.2.11.2 leaves the AMF’s behaviour toward an NSACF that does not answer to operator policy. This AMF’s policy is to degrade open: if no NSACF is discoverable, the INCREASE gets no answer (transport error or timeout), the NSACF answers an unexpected status, or it refuses the AMF’s access token, the S-NSSAI is admitted. Nothing was counted, so nothing is counted out later. An INCREASE that may have been applied without an answer gets one precautionary DECREASE. There is no setting to fail closed. An operator that must never exceed a quota while its NSACF is down needs the NSACF to be highly available. Only an explicit denial from the NSACF (403, or a 200 listing the UE in acuFailureList) rejects an S-NSSAI. The rejection is reported once, in that registration’s Accept or Reject: a later Registration Accept that ran no NSAC does not repeat it.

Paging strategy

amf.paging.strategy decides which NG-RAN nodes receive the NGAP PAGING for a CM-IDLE UE. TS 23.501 §5.4.3.1 leaves this to local configuration. The AMF logs the value in effect at startup, as Paging strategy: <value>.

  • registration-area (the default) sends the PAGING to every gNB whose Supported TA List serves the UE’s registration area, on the first attempt and on every T3513 retransmission. This is the behaviour before #1442. The Information on Recommended Cells and RAN Nodes for Paging IE is decoded and not stored. TS 38.413 §8.3.3.2 makes storing it optional (“shall, if supported, store it”), so this is conformant.

  • recommended-first:

    • Storing. The AMF stores the Recommended RAN Nodes for Paging (TS 38.413 §9.3.1.101) from the UE CONTEXT RELEASE COMPLETE that moves the UE to CM-IDLE. They are kept in the RAN’s order: visited nodes, most recent first, each followed by its associated non-visited nodes.
    • Matching. A RAN node matches a gNB or ng-eNB by the whole Global RAN Node ID (PLMN, gNB ID and its bit length) it gave at NG Setup. A TAI entry matches the nodes serving that TAI. An N3IWF entry is ignored.
    • First attempt. The PAGING goes only to the recommended nodes that also serve the registration area, in that order. A recommended node outside the area is not paged, because the PAGING names the area’s TAI. TS 23.502 §4.2.3.3: when the information is available the AMF “shall take that information into account”.
    • Retransmissions. Every T3513 retransmission (AMF_T3513_SECS) widens to the whole registration area.
    • Falling back. If the recommendation matches no connected node in the area, the first attempt already pages the whole area. The same applies when the RAN sent no recommendation, and when the release or its IE was unusable.
    • Clearing. The stored list belongs to one idle period. A release whose Complete carries no IE clears it. A CM-IDLE entry with no UE CONTEXT RELEASE COMPLETE also clears it: NG Reset, loss of the gNB’s association, or an Initial Context Setup Failure.
    • The Recommended Cells for Paging are transparent to the 5GC (§9.3.1.71) and are not kept. Assistance Data for Recommended Cells is not sent. Paging Attempt Information is sent; see Paging Attempt Information.

  • nwdaf-mobility (nextgsim#464). TS 23.501 §5.4.3.1: “If NWDAF is deployed, the AMF may also use analytics … on the UE’s mobility as provided by NWDAF”. The AMF is the UE Mobility consumer of TS 23.288 §6.7.2.

    • Asking. When a page is queued for a UE with a SUPI, the AMF sends Nnwdaf_AnalyticsInfo_Request to an NWDAF: GET /nnwdaf-analyticsinfo/v1/analytics?event-id=UE_MOBILITY&tgt-ue={"supis":[..]}&ana-req={"endTs":now+30s} (TS 29.520 §4.3.2.2.2). Because the window is in the future, the NWDAF returns a prediction.
      • There is no startTs (#1504). When it is absent, the period starts at the present time at the NWDAF (TS 29.520 Table 5.1.6.2.7-1), so the window starts at the NWDAF’s present and is a prediction, unless the NWDAF’s clock runs 30 s or more ahead of the AMF’s. In that case endTs is already past at the NWDAF, and it answers statistics, which the AMF does not page as a prediction (see the statistics case under Falling back). A startTs of the AMF’s now would be wrong. It is written in whole seconds and is already past when the request arrives. With a future endTs, that period starts in the past and ends in the future. TS 29.520 §4.3.2.2.2 requires the NWDAF to reject such a period with 400 BOTH_STAT_PRED_NOT_ALLOWED.
      • The NWDAF is found in the discovery cache, then by NRF discovery for nnwdaf-analyticsinfo, then through NWDAF_SBI_ADDR/NWDAF_SBI_PORT.
      • The request carries an OAuth2 token when sbi.oauth2 is configured.
      • The query runs off the NGAP task.
    • The NWDAF must serve UE Mobility. In this repository that means nwdafd built with --features amf-mobility and run with nwdaf.amf_mobility.enabled: true (or demo d441c-amf-mobility mode on). It learns cells from this AMF’s LOCATION_REPORT events, sent on Handover Notify and Path Switch. Without it, nwdafd answers 204 and every page falls back to the registration area, after up to 300 ms.
    • Holding. Only that UE’s first PAGING waits for the answer, for at most 300 ms, NRF discovery included. The pump does not wait on the NWDAF, and every other page goes out as usual. At most 64 queries are in flight. Past that, a page is released at once to the registration area. A warning is logged at most once every 10 s, with the count of pages it covers.
    • First attempt. The PAGING goes to the connected gNBs that own the predicted cell, then to the gNB that owns the UE’s last known cell, each once and only if it serves the registration area. A gNB owns a cell when its Global gNB ID (PLMN, and gNB ID at its own bit length) equals the NCGI’s PLMN and the leftmost gNB-ID-length bits of the NCI (TS 38.413 §9.3.1.7). The last known cell is paged as well because the NWDAF predicts the most likely next cell: a UE that has not moved since it went idle is still where the AMF last saw it.
    • Retransmissions. Every T3513 retransmission widens to the whole registration area.
    • Falling back. In each of these cases the first attempt pages the whole registration area:
      • the UE has no SUPI;
      • the 64-query cap is full;
      • no NWDAF is found;
      • the connection is refused, or there is no answer within 300 ms;
      • the answer is not 200 (204: no data);
      • the body names no NR cell;
      • the body is statistics, not a prediction: no locInfos entry carries a confidence, which TS 29.520 Table 5.1.6.2.11-1 requires of a prediction (#1508). The NWDAF answers statistics when its clock reads the requested period as already past, that is when the AMF’s clock runs 30 s or more behind the NWDAF’s. Keep the two within a few seconds (NTP); a skewed pair counts every page as no_prediction;
      • neither the predicted cell nor the last known one is owned by a connected gNB in the area;
      • the answer arrives after the first PAGING. A late answer is not used for that page.
    • RAN sharing. A cell whose NCGI carries a broadcast PLMN other than the Global gNB ID’s PLMN matches no gNB, so it falls back as above.
    • Observability. amf_paging_nwdaf_hints_total{outcome}, with outcome predicted, no_prediction, error, timeout, cap_full or late, is exported only under this strategy. The info lines NWDAF UE mobility: ue=<supi> predicted=(<plmn>, 0x<nci>) confidence=<n>% and ... <role> cell 0x.. is served by gNB 0x.. show the prediction and the gNBs it mapped to.
    • Assistance Data for Recommended Cells is not sent. Paging Attempt Information is sent; see Paging Attempt Information.

The paging log line keeps its prefix in every mode:

  • Paging sent to N/M gNB(s) serving the registration area: ...;
  • ... recommended by the RAN in the registration area: ... for a recommended first attempt;
  • ... predicted by NWDAF UE mobility in the registration area: ... for an NWDAF-steered first attempt that pages a predicted gNB;
  • ... at the UE's last known cell in the registration area (no gNB owns the NWDAF prediction): ... when no gNB in the area owns the prediction and only the last known cell’s gNB is paged.

Paging Attempt Information

Under recommended-first and nwdaf-mobility, every PAGING carries an Assistance Data for Paging IE holding only Paging Attempt Information (TS 38.413 §9.3.1.69, §9.3.1.72; nextgsim#464). Its fields are:

  • Paging Attempt Count: the attempt number, 1 for the first PAGING. Each T3513 retransmission adds one (TS 38.300 §9.2.5).
  • Intended Number of Paging Attempts: the first attempt plus the T3513 retransmissions (5 by default).
  • Next Paging Area Scope: changed when this attempt pages fewer gNBs than the registration area (a recommended or predicted first attempt), since the next attempt pages the whole area. Otherwise same. It is left out on the last attempt, after which there is no next one.

Each attempt is a single PDU sent to every gNB paged in that attempt, so they all receive the same value (TS 23.502 §4.2.3.3). Both values stay within INTEGER (1..16). The default registration-area strategy sends no Assistance Data for Paging, and its PAGING is unchanged.

Demo block

amfd reads the shared demo: block at the root of its config file (nextgsim#458). Its enabled key is the process kill switch, and each demo is configured under its own key with enabled and mode. The block is checked against the demos the binary was built with. An unknown key fails startup, as does an unknown mode or a demo whose cargo feature is not built. A default build registers no demo, so any demo.<key> entry there fails startup. With no demo active, amfd is unchanged.

Unauthenticated emergency service

Set this key deliberately. amf.emergency.allow_unauthenticated decides whether an emergency call connects when the AMF cannot authenticate the caller. In some jurisdictions the answer is legally mandatory; in others the feature is forbidden. The shipped default is true, and it is not the right value everywhere.

What the setting does

When a UE sends a REGISTRATION REQUEST whose 5GS registration type is Emergency Registration and the AMF cannot obtain an authentication vector — the AUSF is unreachable, or refuses the request — the AMF has two conformant options, and this key chooses between them.

true (default): proceed unauthenticated. The AMF continues the registration without authentication, per TS 33.501 §10.2.2.2 (“If the AMF cannot identify the subscriber, or cannot obtain authentication vector (when SUPI is provided), the AMF shall send NAS SMC with NULL algorithms to the UE”). Concretely:

  • NIA0 and NEA0 are forced, not negotiated, regardless of the algorithms the UE advertised (TS 33.501 §6.7.3.6). The session has no NAS integrity protection and no NAS ciphering.
  • K_AMF is generated locally from the OS CSPRNG, per TS 33.501 §10.2.2.3.1 (“the UE and the AMF independently generate the K_(AMF) in an implementation defined way”). The UE generates its own; the two never match, and nothing requires them to, because NIA0 computes no MAC and NEA0 enciphers nothing.
  • No UDM, PCF or NSACF interaction. TS 23.502 §4.12.2.3: “if the UE was not successfully authenticated, the AMF shall not update the UDM … the AMF shall not check for access restrictions, regional restrictions or subscription restrictions”, and AM/UE policy “are not required for Emergency Registration”. So no subscription is fetched and no SUPI is registered at the UECM.
  • No Allowed NSSAI is sent in the Registration Accept (same clause).
  • The Registration Accept reports the UE Emergency registered (TS 24.501 §9.11.3.6 octet 3 bit 6).
  • Only emergency PDU sessions. A UE registered for emergency services, authenticated or not, may establish only emergency PDU sessions (TS 23.501 §5.16.4.9a: “the network shall reject any PDU Session Establishment request for normal service from the UE on this Access Type”). A request whose Request type is not “initial emergency request” or “existing emergency PDU session” is sent back before an SMF is selected. The answer is a DL NAS TRANSPORT carrying the 5GSM message and 5GMM cause #90 “payload was not forwarded” (TS 24.501 §5.4.5.2.5 a) 20), §5.4.5.3.1 case e); #2041). An emergency request, “initial emergency request” or “existing emergency PDU session”, goes to the SMF on the emergency DNN and emergency.s_nssai, whatever the UE named (§5.4.5.2.5 a) v), vii), viii)).
  • The UE security capabilities conveyed to the gNB are narrowed to the null set (TS 33.501 §6.7.3.6).

false: refuse. The registration is rejected and the UE released, exactly as an ordinary registration with an unreachable AUSF would be. Set this where local regulation forbids unauthenticated emergency service — TS 33.501 §5.1.2: “Serving networks located in regions where unauthenticated emergency services are forbidden shall not support this feature.”

Why the default is true

TS 33.501 §5.1.2 imposes two obligations pointing opposite ways: the 5G system “shall support unauthenticated access for emergency services … only to those serving networks where regulatory requirements for unauthenticated emergency services exist”, and networks where it is forbidden “shall not support this feature”. A shipped default must pick one, and the two are not symmetric:

  • An operator deploying into a forbidding jurisdiction knows that fact and can set the key. The spec expects this: TS 33.501 §10.2.2.2 says “It shall be possible to configure whether the network allows or rejects an emergency registration request”.
  • A default of false would make the software non-conformant out of the box in every jurisdiction where unauthenticated emergency calling is mandatory — and it fails in the direction where the failure is a caller who cannot reach a PSAP.

The worst case under true is an unauthenticated device obtaining an emergency-only, null-ciphered, single-DNN, no-subscription session — which is precisely the fenced session TS 33.501 §10.2.2 and TS 23.501 §5.16.4.9a specify for this case. The worst case under false is an emergency call that does not connect. The full argument, with the rejected alternatives, is in specs/decide-unauthenticated-emergency-registration.md.

Operational notes

  • Every unauthenticated emergency registration logs at warn, twice: once when the AMF decides to continue without authentication, and once when it sends the Security Mode Command with NULL algorithms. A refusal under false also logs at warn, naming the setting. Neither case is silent.
  • The setting is read once at startup. Changing it requires an AMF restart.
  • An emergency registration that does authenticate successfully is unaffected by this key: it keeps a real key hierarchy, a real SUPI, its UDM subscription and a non-NULL integrity algorithm. It is still reported “Emergency registered” and still restricted to the emergency DNN, because that restriction follows from the registration type rather than from the authentication outcome.

Current limitations

  • Authentication failure is still refused, regardless of this setting. Only the inability to obtain a vector takes the unauthenticated path. A UE that answers with 5GMM cause #20 (MAC failure), or an AUSF that answers AUTHENTICATION_FAILURE, is refused. TS 33.501 §10.2.2.2 would permit NULL algorithms there too; it is not yet implemented.
  • No PEI-only (UICC-less) registration. TS 33.501 §10.2.2.1 behaviour (b) admits UEs presenting only a PEI. This AMF’s registration parser accepts SUCI and 5G-GUTI identities only, so a credential-less UE is refused before the emergency path is reached. This implements §10.2.2.1 behaviour (a), “IMSI required, authentication optional”, and not (b).
  • No IMS leg. The emergency PDU session is established on the emergency DNN and a P-CSCF address is configurable, but there is no IMS core in this tree, so no SIP INVITE reaches a PSAP.
  • The EPC/MME path is unchanged. An emergency attach over S1 (nextgcore-mmed) is recognised and recorded but follows the normal authentication path; see specs/fix-mmed-attach-tau-accept-correctness.md.
