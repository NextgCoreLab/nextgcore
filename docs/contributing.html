Contributing Guide

NextGCore is a research-faithful 5G core in Rust (3GPP Rel-15 baseline + selected Rel-17/18 features; 6G items are non-normative prototypes). This guide covers everything from a clean machine to a merged pull request.

What to work on Environment Building Testing Code style 3GPP references Submitting a PR Getting merged License & DCO

1. How to contribute — finding work

  • Good first targets: any row marked partial or prototype in the supported-features matrix — each names the service, procedures, and the governing 3GPP spec.
  • Known gaps: the gap-analysis docs in docs/ (protocols, libraries, 6G) list concrete missing procedures with spec references.
  • Bugs & proposals: open a GitHub issue first for significant changes (new NF surfaces, new dependencies, protocol-behavior changes) so the approach can be agreed before you invest in code.

3. Building

The Cargo workspace root is nextgcore/src/, not the repo root.

cd src cargo build --workspace # debug cargo build --workspace --release # release cargo build -p nextgcore-amfd # a single NF binary

4. Testing

cd src cargo test --workspace # all unit + integration tests cargo test -p nextgcore-amfd # a single NF cargo test --workspace -- --nocapture # with log output # E2E against the matched RAN simulator (requires Docker) cd ../docker/rust && bash e2e.sh bash e2e-test.sh --no-build --keep # iterate without rebuilding

Honesty rule: E2E validation runs against the matched NextGSim UE/gNB — it proves internal consistency, not third-party conformance. Never claim spec conformance in code, docs, or commit messages beyond what the tests actually demonstrate.

5. Code style & pre-commit checklist

cd src cargo fmt --all cargo clippy --workspace -- -D warnings cargo test --workspace cargo audit # cargo install cargo-audit
  • Zero clippy warnings and zero cargo fmt diffs — CI enforces both.
  • Every new NF binary must: register with NRF on startup, expose Prometheus /metrics, shut down gracefully on SIGTERM, and log via RUST_LOG.
  • ≥ 1 unit test per public function on new code.

6. 3GPP specification references

Every protocol file carries a doc comment citing its spec (e.g. //! TS 23.502 §4.2.2). When you add or change protocol logic, cite the exact TS and section: TS 23.501/23.502 (architecture/procedures), TS 24.501 (NAS), TS 29.xxx (SBI services), TS 38.413 (NGAP), TS 29.244 (PFCP). PRs that add protocol behavior without a spec reference will be asked to add one.

7. Submitting a pull request

  1. Create a feature branch from main with a descriptive name.
  2. Keep PRs small and focused — one logical change per PR; split large work into a reviewable series.
  3. Use conventional-commit titles that name the NF and the spec item:
feat(smf): add MBS multicast session context (TS 23.247) fix(amf): release SMF session on UE context release test(upf): add SDF filter 5-tuple matching unit tests
  • Sign every commit: git commit -s → Signed-off-by: Your Name <email> (Developer Certificate of Origin).
  • Never include AI attributions (e.g. Co-Authored-By bot trailers).
  • The PR description should state what changed, why, the governing 3GPP TS item, and how it was tested.

8. Getting your PR merged

CI must be green before review: cargo check, cargo test --workspace (flake-retried once), cargo clippy, and cargo fmt --check all run on every push. A maintainer reviews for correctness, spec fidelity, and test coverage; address review comments with follow-up commits (no force-push during review). Docs changes to docs/ deploy to this site on release or manual dispatch of the Deploy to GitHub Pages workflow.
