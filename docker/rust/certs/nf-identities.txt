# NF identities of the shipped dev stacks (issue #1617).
#
# One line per NF: <cert name> <nfType> <nfInstanceId> <addresses>
#
# generate-dev-certs.sh issues <cert name>.crt with the TLS client/server
# profile of TS 33.310 §6.1.3c.3: subjectAltName URI-ID urn:uuid:<nfInstanceId>
# and the RFC 9310 NFTypes extension naming <nfType>. The NRF binds
# NFRegister / NFUpdate / NFDeregister to both (#1611), so each value here
# must be what that NF actually registers:
#   - <nfInstanceId> is pinned in the stack by NEXTGCORE_<TYPE>_INSTANCE_ID
#     (src/libs/nextgcore-sbi/src/nf_instance_id.rs). A generated UUID would
#     not match any certificate.
#   - <nfType> is the nfType the daemon puts in its NFProfile, in the
#     TS 29.510 §6.1.6.3.3 enumeration that TS 33.310 §6.1.3c.3 requires for
#     NFTypes (mbsmfd registers "MB_SMF"; #1680 tracks the "MBSMF" spelling
#     still used by nextgcore_sbi::NfType and its instance-ID variable).
# check-nf-identities.py fails CI when a compose file pins a different ID.
#
# <addresses> is a comma-separated list of the NF's IP addresses on the
# stack's networks (docker-compose.yml), or - for none. They become IP SANs
# next to DNS:<cert name> and DNS:nextgcore-<cert name> (loopback only with
# generate-dev-certs.sh --loopback).
#
# nfInstanceId is a UUID version 4 (TS 29.571 §5.3.2): the 13th hex digit is
# 4 and the 17th is 8.
#
# scp and sepp do not register with the NRF; their certificates still carry
# a URN, which TS 33.310 §6.1.3c.4 / §6.1.3c.5.2 require of them too.
